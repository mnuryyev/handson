## Введение
Каждый раз, когда в адресной строке браузера появляется замок и буквы HTTPS, между устройством и сервером происходит сложный криптографический процесс - **TLS Handshake**. Именно он гарантирует три вещи: что мы общаемся именно с тем сервером (аутентификация), что данные не могут быть прочитаны третьими лицами (конфиденциальность) и что они не были изменены в пути (целостность).
В данной работе рассмотрим протокол **SSL/TLS** как с теоретической точки зрения, так и проведём полную практическую демонстрацию. Перехватим и разберём **TLS handshake** в Wireshark, проанализируем сертификаты, проверим конфигурацию реальных серверов на уязвимости и воспроизведём последствия использования устаревших версий протокола.



## Теоретическая база

### История: от SSL к TLS

Протокол **SSL (Secure Sockets Layer)** был разработан компанией Netscape в 1994 году для защиты HTTP-трафика. За три десятилетия он прошёл путь от уязвимых ранних версий до современного **TLS 1.3**.

| Версия   | Год  | Статус                | Причина устаревания / Примечания               |
|----------|------|----------------------|-----------------------------------------------|
| SSL 2.0  | 1995 | Запрещён (RFC 6176)  | Критические уязвимости в дизайне             |
| SSL 3.0  | 1996 | Запрещён (RFC 7568)  | Атака POODLE (2014)                           |
| TLS 1.0  | 1999 | Устарел (RFC 8996)   | Атаки BEAST, POODLE-TLS                       |
| TLS 1.1  | 2006 | Устарел (RFC 8996)   | Слабые алгоритмы, отключён в 2021             |
| TLS 1.2  | 2008 | Актуален             | Безопасен при правильной конфигурации         |
| TLS 1.3  | 2018 | Рекомендован         | Упрощённый handshake, Forward Secrecy         |


### Ключевые понятия

Асимметричное шифрование **(RSA, ECDH)**

Использует пару ключей: **публичный и приватный**. Публичный ключ вшит в сертификат и доступен всем. Приватный ключ хранится только на сервере. Применяется только на этапе handshake для безопасного обмена симметричным ключом - из-за высокой вычислительной стоимости.

Симметричное шифрование **(AES-GCM, ChaCha20)**

После handshake весь трафик шифруется быстрым симметричным алгоритмом с сессионным ключом, который был согласован на предыдущем этапе. Это обеспечивает высокую производительность при передаче данных.

Forward Secrecy (PFS) - **совершенная прямая секретность**

Ключевое свойство TLS 1.3: для каждой сессии генерируется уникальный временный ключ (через ECDHE). Даже если приватный ключ сервера будет скомпрометирован в будущем - расшифровать ранее перехваченный трафик будет невозможно.


### Структура TLS Handshake (TLS 1.3 — упрощённая)

- ClientHello - клиент сразу отправляет поддерживаемые группы и параметры key_share.
- ServerHello + EncryptedExtensions + Certificate + Finished - всё в одном ответе.
- Client Finished - клиент подтверждает. Соединение установлено.

> TLS 1.3 полностью отказался от устаревших алгоритмов: RSA key exchange, RC4, DES, 3DES, MD5, SHA-1 для подписей. Оставлены только современные: AES-GCM, ChaCha20-Poly1305, ECDHE.

![07_wireshark_tls](/handson/images/ssl_tls_sec/07_wireshark_tls.png)

### Шаг 4. Анализ ClientHello

В списке пакетов находим первый TLS-пакет с меткой **Client Hello**. Кликаем на него. В нижней панели Wireshark раскрываем секцию Transport Layer Security → TLSv1.2 Record Layer → Handshake Protocol: Client Hello.
Что мы видим в ClientHello:
- Version - максимальная версия TLS, которую поддерживает клиент (например, TLS 1.2).
- Random - 32 байта случайных данных (Client Random). Используется при генерации сессионного ключа.
- Session ID - если это повторное подключение, здесь будет ID предыдущей сессии.
- Cipher Suites - список алгоритмов шифрования, которые поддерживает клиент (обычно 10–30 вариантов).
- Extensions - дополнительные возможности: SNI (имя сервера), поддержка ALPN (HTTP/2), supported_groups.

![08_clienthello](/handson/images/ssl_tls_sec/08_clienthello.png)

**SNI (Server Name Indication)** - особо важное расширение. Оно позволяет серверу понять, к какому сайту обращается клиент, и отдать правильный сертификат. Без SNI один IP-адрес мог бы использовать только один сертификат.

### Шаг 5. Анализ ServerHello и выбора Cipher Suite

Находим пакет Server Hello. Раскрываем его структуру аналогичным образом. Ключевое поле — Cipher Suite: здесь сервер выбрал один алгоритм из предложенного клиентом списка.
Пример типичного выбора для TLS 1.2:
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
Расшифровка этой строки:
- TLS - протокол.
- ECDHE - метод обмена ключами (Elliptic Curve Diffie-Hellman Ephemeral). Обеспечивает Forward Secrecy.
- RSA - алгоритм аутентификации сервера (проверяется через сертификат).
- AES_256_GCM - симметричный алгоритм шифрования данных (256-битный ключ, режим GCM).
- SHA384 - алгоритм для HMAC (проверка целостности сообщений).

![09_serverhello](/handson/images/ssl_tls_sec/09_serverhello.png)


### Шаг 6. Анализ сертификата сервера

Находим пакет **Certificate**. В нём содержится цепочка X.509-сертификатов: сертификат сайта, промежуточный CA и корневой CA. Раскрываем Certificate → Certificates → Certificate.
Ключевые поля для анализа:
- Subject - кому выдан сертификат (Common Name = доменное имя).
- Issuer - кем выдан (Certificate Authority, например Let's Encrypt).
- Validity - срок действия (Not Before / Not After).
- Subject Alternative Names (SAN) - список доменов, на которые распространяется сертификат.
- Public Key - публичный ключ сервера (тип и размер: RSA 2048, EC 256 и т.д.).
- Signature Algorithm - алгоритм подписи CA (должен быть SHA-256 или лучше).

![10_analyze_cert](/handson/images/ssl_tls_sec/10_analyze_cert.png)


### Шаг 7. Наблюдение ChangeCipherSpec и завершения Handshake

После обмена ключами в списке пакетов появляются:
- Change Cipher Spec (клиент) - уведомление.
- Encrypted Handshake Message (клиент) - зашифрованное сообщение Finished.
- Change Cipher Spec (сервер) - ответное уведомление от сервера.
- Encrypted Handshake Message (сервер) - зашифрованный Finished от сервера.

После этого все последующие пакеты имеют тип Application Data - это уже зашифрованный HTTP-трафик, содержимое которого без ключа увидеть невозможно.

![11_changecipher](/handson/images/ssl_tls_sec/11_changecipher.png)

### Шаг 11. Проверка срока действия сертификата

Автоматизируем проверку срока истечения сертификата - это полезный скрипт для мониторинга инфраструктуры:

```
#!/bin/bash
DOMAIN='badssl.com'
EXPIRY=$(echo | openssl s_client -connect ${DOMAIN}:443 2>/dev/null \
  | openssl x509 -noout -enddate | cut -d= -f2)
echo "Сертификат $DOMAIN истекает: $EXPIRY"

# Проверяем, сколько дней осталось
DAYS=$(( ( $(date -d "$EXPIRY" +%s) - $(date +%s) ) / 86400 ))
echo "Осталось дней: $DAYS"

if [ $DAYS -lt 30 ]; then
  echo 'ПРЕДУПРЕЖДЕНИЕ: сертификат истекает менее чем через 30 дней!'
fi
```

### Шаг 19. POODLE - объяснение атаки на SSL 3.0

POODLE (Padding Oracle On Downgraded Legacy Encryption) - атака 2014 года на SSL 3.0. Суть: злоумышленник, находясь в позиции MITM, может принудительно «понизить» соединение с TLS до SSL 3.0 (downgrade attack), а затем использовать уязвимость в режиме CBC для расшифровки трафика по одному байту.

Проверяем, поддерживает ли сервер устаревший протокол SSL 3.0 (он должен отклонить соединение с ошибкой рукопожатия), затем дополнительно проверяем его на уязвимость к атаке POODLE с помощью сканирования и убеждаемся, что он неуязвим, а для сравнения выполняем ту же проверку на заведомо уязвимом сервере.

## Итоги и выводы

### Сравнение версий TLS по безопасности

| Параметр                | TLS 1.1                | TLS 1.2                          | TLS 1.3                          |
|-------------------------|------------------------|----------------------------------|----------------------------------|
| Статус                  | Отключён с 2021        | Актуален                         | Рекомендован                     |
| RTT для handshake       | 2 RTT                  | 2 RTT                            | 1 RTT (0-RTT при resumption)     |
| Forward Secrecy         | Опционально            | Опционально                      | Обязательно                      |
| Поддерживаемые шифры    | RC4, 3DES, слабые      | AES-GCM, ChaCha20 + устаревшие   | Только современные               |
| Аутентификация          | RSA, DSA               | RSA, ECDSA, DSA                  | RSA, ECDSA (без устаревших)      |

В ходе данной работы был исследован механизм SSL/TLS Handshake - фундаментального процесса, обеспечивающего безопасность современного интернета. Мы рассмотрели эволюцию протокола от уязвимого SSL 2.0 до современного TLS 1.3, захватили и разобрали реальный handshake в Wireshark, провели аудит TLS-конфигурации серверов, создали собственный CA и TLS-сервер, а также продемонстрировали, к каким последствиям приводит использование устаревших версий протокола и слабых cipher suites.
