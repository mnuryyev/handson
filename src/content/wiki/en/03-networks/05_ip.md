IP (Internet Protocol) is a network layer protocol (OSI L3) responsible for addressing and routing packets between hosts. Defined in RFC 791 (1981) for IPv4. IP is unreliable and connectionless: it does not guarantee delivery, ordering, or absence of duplicates. These tasks are handled by transport layer protocols (TCP).

## IPv4 Header Fields

### Version (4 bits)

```
IP protocol version.
4 = IPv4
6 = IPv6

The value 4 (0100 in binary) is present in every IPv4 packet.
A router looks at this field first.
```

### IHL - Internet Header Length (4 bits)

```
Header length in 32-bit words (4 bytes each).

Minimum: 5 (5 x 4 = 20 bytes - header without options)
Maximum: 15 (15 x 4 = 60 bytes - header with options)

Why needed? The Options field has variable length.
IHL tells where the header ends and data begins.

Formula: start of data = IHL x 4 bytes from packet start
```

### DSCP and ECN (formerly: Type of Service, 8 bits)

```
DSCP (Differentiated Services Code Point, 6 bits):
Packet priority for QoS (Quality of Service).

Common DSCP values:
  000000 (CS0/BE) - Best Effort, normal traffic
  001000 (CS1)    - low priority
  010000 (CS2)    - standard
  011000 (CS3)    - signaling (VoIP setup)
  100000 (CS4)    - video
  101000 (CS5)    - voice (VoIP)
  110000 (CS6)    - network protocols (OSPF, BGP)
  111000 (CS7)    - reserved

Common predefined values (Expedited/Assured Forwarding):
  EF  (101110) - Expedited Forwarding (VoIP, real-time)
  AF11-AF43    - Assured Forwarding (different classes and drop precedences)

ECN (Explicit Congestion Notification, 2 bits):
  00 - Non ECN-Capable Transport
  01 or 10 - ECN Capable Transport (ECT)
  11 - Congestion Experienced (CE) - router detected congestion
```

### Total Length (16 bits)

```
Full size of the IP packet: header + data (in bytes).

Minimum: 20 bytes (header only, no data)
Maximum: 65535 bytes

In practice packets rarely exceed MTU (1500 bytes for Ethernet).
Packets larger than MTU must be fragmented.

Useful:
  Data size = Total Length - (IHL x 4)
```

### Identification (16 bits)

```
Unique identifier for a group of fragments.

Purpose:
- All fragments of the same packet share the same Identification.
- The receiver uses it to reassemble fragments.

Generation:
- Usually a monotonically increasing counter (per source, per dest).
- Some OSes use random values (for security).

If packet is not fragmented (DF=1):
- Field is still set (RFC 791 rule).
- But not actually used in reassembly.
```

### Flags (3 bits)

```
Three bits controlling fragmentation:

Bit 0 (Reserved, Evil Bit): always 0
  Reserved. RFC 3514 ("Evil Bit") - a humorous RFC
  proposing to set this bit for malicious packets.

Bit 1 - DF (Don't Fragment):
  0 - fragmentation allowed
  1 - fragmentation prohibited

  With DF=1 and packet > MTU, the router:
  - drops the packet
  - sends ICMP "Fragmentation Needed" (Type 3, Code 4) to the sender

  Used in:
  - Path MTU Discovery (PMTUD)
  - TCP MSS negotiation
  - GRE, IPsec tunnels

Bit 2 - MF (More Fragments):
  0 - this is the last (or only) fragment
  1 - more fragments follow this one

  Last fragment: MF=0, Fragment Offset > 0
  Non-fragmented packet: MF=0, Fragment Offset=0

Examples:
  Flags = 0x00 (000) - not fragmented, last
  Flags = 0x40 (010) - DF=1, do not fragment
  Flags = 0x20 (001) - MF=1, intermediate fragment
```

### Fragment Offset (13 bits)

```
Position of this fragment within the original packet.
Measured in 8-byte blocks (not bytes!).

Actual byte offset = Fragment Offset x 8

Maximum offset: 8191 x 8 = 65528 bytes

Why x 8?
  13 bits give max 8191, multiply by 8 = 65528 bytes.
  This nearly covers the IPv4 maximum (65535 bytes).
  Step of 8 bytes - every fragment (except the last) must
  have a data length divisible by 8 bytes.

Example for a 4000-byte packet, MTU=1500:
  Fragment 1: offset=0    (bytes 0-1479)
  Fragment 2: offset=185  (185 x 8 = 1480, bytes 1480-2959)
  Fragment 3: offset=370  (370 x 8 = 2960, bytes 2960-3999)
```

### TTL - Time To Live (8 bits)

Covered in detail in a dedicated section below.

### Protocol (8 bits)

```
Upper layer protocol (what is in the data field).

IANA values:
  1   - ICMP  (ping, traceroute)
  2   - IGMP  (multicast)
  6   - TCP   (reliable delivery)
  17  - UDP   (connectionless)
  41  - IPv6  (encapsulated)
  47  - GRE   (tunnels)
  50  - ESP   (IPsec, encryption)
  51  - AH    (IPsec, authentication)
  89  - OSPF  (routing)
  132 - SCTP

See full list:
  cat /etc/protocols
```

### Header Checksum (16 bits)

```
Checksum of the IP header ONLY (not the data!).
Data is protected by L4 protocols (TCP/UDP checksum).

Key behavior: recalculated by every router.
Why? TTL decreases at each hop → header changes
→ old checksum becomes invalid.

Algorithm: one's complement sum of all 16-bit words in the header.

If checksum does not match → packet is dropped silently (no notification).
```

### Source and Destination IP (32 bits each)

```
Source IP      - sender's address
Destination IP - receiver's address

Both in IPv4 format (4 octets of 8 bits each).
Example: 192.168.1.10 = 0xC0A8010A

Important: Source IP can be forged (IP spoofing).
Routers do not verify whether the sender actually owns the address.
Protection - BCP38 (ingress filtering) at network borders.
```

### Options (0-40 bytes)

```
Optional fields. Rarely used in modern networks
(they interfere with hardware offloading, often blocked by firewalls).

Examples of options:
  Record Route (7)    - each router records its IP
  Timestamp (68)      - each hop adds a timestamp
  Strict Source Route - rigidly defined path (all hops specified)
  Loose Source Route  - some hops specified
  Router Alert (148)  - ask routers to process the packet

Problems:
  Any packet with Options is processed by the router's CPU
  (not the hardware fast path) → slower and potentially exploitable.

They increase IHL: if Options are present, IHL > 5.
```

## TTL - Time To Live

### What TTL Is

```
TTL (Time To Live) - a packet's lifetime counter in the network.
Range: 0-255 (8 bits).

Every router the packet passes through:
  1. Decrements TTL by 1
  2. If TTL reaches 0 → drops the packet
  3. Sends ICMP "Time Exceeded" (Type 11, Code 0) back to the source

Purpose: prevent packets from circulating forever
in case of routing loops.

Important: TTL is measured in hops, NOT seconds.
Although RFC 791 envisioned it as seconds, in practice
each hop = -1 TTL (even if the router processes it instantly).
```

### Default Initial TTL Values

```
OS / Device                    Default TTL
───────────────────────────────────────────
Linux (modern)                      64
Windows (XP+)                      128
macOS / iOS                         64
Cisco IOS (router)                 255
Solaris / AIX                      255
FreeBSD / OpenBSD                   64
Android                             64
Windows 95/NT                      128
Windows 2000/XP (early)             32

These values can be configured:
  Linux:   /proc/sys/net/ipv4/ip_default_ttl
  Windows: HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\DefaultTTL
```

### How TTL Works at Each Hop

```
Sender                R1               R2            Receiver
TTL=64 ──────────────► TTL=63 ────────► TTL=62 ─────►  delivered

If the packet does not reach destination:
TTL=3 ────► TTL=2 ────► TTL=1 ────► TTL=0
                                     ↓
                         R3 drops the packet
                         R3 sends ICMP "Time Exceeded" → to source
                         (ICMP Type 11, Code 0)
```

### OS Detection via TTL (OS Fingerprinting)

```
Knowing the TTL in the reply packet and approximate distance (hops),
you can guess the sender's OS:

ping 8.8.8.8 → TTL=117 in reply
  Typical initial values: 64, 128, 255
  117 is close to 128 - 11 hops → likely Windows

ping linux-host → TTL=62 in reply
  62 is close to 64 - 2 hops → likely Linux/macOS

This is the basis of passive fingerprinting (p0f, nmap -O).
Accuracy decreases if TTL is set to a non-default value.

Practical rule:
  Reply TTL 64±10  → Linux/macOS/FreeBSD (initial 64)
  Reply TTL 128±15 → Windows (initial 128)
  Reply TTL 255±15 → Cisco IOS / Solaris (initial 255)
```

### TTL and traceroute

```
traceroute uses TTL to map the packet path:

1. Send a packet with TTL=1 → first router drops it,
   returns ICMP "Time Exceeded" → we learn the first hop's IP.

2. TTL=2 → second hop returns ICMP → second hop's IP.

3. Repeat until ICMP "Destination Unreachable" or
   ICMP Echo Reply from the target is received.

traceroute implementations:
  Linux (traceroute): UDP packets to ports 33434+ (default)
  Linux (tracepath):  UDP, no root required
  Windows (tracert):  ICMP Echo Request
  TCP variant:        tcptraceroute, hping3 -S

Problem: firewalls often block UDP/ICMP → asterisks (*).
Solution: tcptraceroute (TCP SYN on port 80/443 - usually allowed).
```

```
# traceroute to target
traceroute 8.8.8.8
traceroute -I 8.8.8.8       # ICMP instead of UDP
traceroute -T -p 80 8.8.8.8 # TCP SYN on port 80
traceroute -n 8.8.8.8       # no DNS resolution

# Windows
tracert 8.8.8.8

# Show TTL in ping reply
ping -c 3 8.8.8.8

# View TTL of a packet in tcpdump
tcpdump -i eth0 -v 'icmp'
# 192.168.1.10 > 8.8.8.8: ICMP echo request, id 1, seq 1, length 64
# (tos 0x0, ttl 64, id 12345, offset 0, flags [DF], ...)

# Change outgoing TTL (Linux)
ping -t 5 8.8.8.8            # macOS: -m 5
hping3 --ttl 5 8.8.8.8       # set exact TTL

# Change system default TTL
echo 128 > /proc/sys/net/ipv4/ip_default_ttl

# Make it persistent (via sysctl)
echo "net.ipv4.ip_default_ttl = 128" >> /etc/sysctl.conf
sysctl -p
```

### TTL and Security

```
TTL-based attacks and techniques:

1. TTL-based evasion:
   An IDS/IPS sees a packet with TTL=1, but the target host won't.
   An attacker can craft packets that the IDS sees
   but the host does not (or vice versa). Basis of some IDS evasion techniques.

2. IP Spoofing + low TTL:
   Packets with forged src IP and TTL=1 → won't reach the spoofed victim,
   but may cause ICMP "Time Exceeded" replies toward the forged address.

3. Network topology discovery (reconnaissance):
   Analyzing TTL in responses to map network topology.

4. Routing loops:
   TTL is the only protection against packets looping indefinitely.
   Without TTL: a packet could circulate forever in a routing loop.
```

## IP Fragmentation

### Why Fragmentation Exists

```
Different network technologies have different MTU (Maximum Transmission Unit):

Technology              MTU (bytes)
────────────────────────────────────
Ethernet                 1500
Wi-Fi (802.11)           2304
PPPoE (DSL)              1492
Loopback                65536
GRE tunnel               1476 (1500 - 24 GRE header)
IPsec (ESP)             ~1422 (depends on cipher/auth)
VXLAN                    1450

If an IP packet > MTU of the next hop:
  - without DF: the router fragments the packet into pieces <= MTU
  - with DF=1: the router drops and sends ICMP "Fragmentation Needed"
```

### How Fragmentation Works

```
Original packet: 4000 bytes of data, MTU=1500

IP header: 20 bytes
Data: 4000 bytes
Total: 4020 bytes > 1500 (MTU)

Per fragment:
  Max data per fragment = MTU - IP header = 1500 - 20 = 1480 bytes
  1480 must be divisible by 8 (for Fragment Offset)
  1480 / 8 = 185 → divides evenly, good

Fragmenting 4000 bytes of data:
┌─────────────────────────────────────────────────────────┐
│  Fragment 1                                              │
│  IP header: ID=12345, MF=1, Offset=0, Total=1500        │
│  Data: bytes 0-1479 (1480 bytes)                         │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│  Fragment 2                                              │
│  IP header: ID=12345, MF=1, Offset=185, Total=1500      │
│  Data: bytes 1480-2959 (1480 bytes)                      │
│  (Offset 185 x 8 = 1480)                                 │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│  Fragment 3                                              │
│  IP header: ID=12345, MF=0, Offset=370, Total=1060      │
│  Data: bytes 2960-3999 (1040 bytes)                      │
│  (Offset 370 x 8 = 2960)                                 │
│  (MF=0 - this is the last fragment!)                     │
└─────────────────────────────────────────────────────────┘
```

### Fragmentation Rules (RFC 791)

```
1. All fragments of the same packet share the same Identification.

2. All fragments (except the last) must have a data length
   divisible by 8 bytes.
   (required by Fragment Offset, which is counted in 8-byte units)

3. MF=1 for all fragments except the last.

4. Last fragment: MF=0, Offset > 0 (if fragmentation occurred).

5. Each fragment is a complete IP packet with its own header.
   Routers can fragment fragments again.

6. Reassembly happens only at the destination host,
   NOT at intermediate routers.
   (Unlike IPv6, where routers cannot fragment at all)

7. Reassembly timeout: if not all fragments arrive within ~15-30 sec →
   all received fragments are discarded,
   ICMP "Time Exceeded, Fragment Reassembly" (Type 11, Code 1) → to source.
```

### Reassembly at the Receiver

```
The receiver reconstructs the original packet:

1. When the first fragment arrives (MF=1 or Offset>0):
   - A reassembly buffer is created, keyed by: (src IP, dst IP, Protocol, ID)
   - A timer starts (usually 15-30 seconds)

2. Each new fragment is placed into the buffer at its Offset position.

3. Reassembly is complete when:
   - A fragment with MF=0 is received (we know the full size)
   - All bytes from 0 to the end are present without gaps

4. If the timer expires before full reassembly → ICMP Type 11, Code 1 → to source.

Teardrop attack:
   Overlapping fragments (overlapping offsets)
   caused buffer overflows in old OSes (Windows 95/98/NT).
   Modern OSes handle this correctly.
```

### Path MTU Discovery (PMTUD)

```
Mechanism for automatically finding the minimum MTU along the entire path.
Allows avoiding fragmentation inside the network.

How it works:
1. Sender sets DF=1 (Don't Fragment).
2. Sends a packet sized at the current PMTU (initially - interface MTU).
3. If packet > MTU somewhere on the path:
   - That router drops the packet
   - Sends ICMP Type 3, Code 4 "Fragmentation Needed"
   - The ICMP message includes the next-hop MTU (RFC 1191)
4. Sender reduces PMTU to the value from ICMP.
5. Repeats until packets get through.

Problem: Black Hole PMTUD
   Many firewalls block ICMP Type 3 → sender never receives
   "Fragmentation Needed" → connection hangs.

Symptom: connection establishes (handshake works, small packets go through),
         but large data (HTTP, files) does not transfer.

Solutions for Black Hole:
   TCP MSS Clamping (on routers/firewalls):
     iptables -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
       -j TCPMSS --clamp-mss-to-pmtu

   PLPMTUD (Packetization Layer PMTU Discovery, RFC 4821):
     PMTU discovery at L4 level, without ICMP.
```

```
# View PMTU for a route
ip route get 8.8.8.8
# 8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10 uid 1000
#   cache  mtu 1500

# PMTU cache
ip route show cache

# Manual PMTU test
ping -c 3 -M do -s 1472 8.8.8.8
# -M do = DF bit set
# -s 1472 = 1472 data + 8 ICMP + 20 IP = 1500 (exactly MTU)

# If reply: "Frag needed and DF set (mtu = 1492)"
# - there is a smaller MTU somewhere on the path

# Find PMTU via tracepath (no root required)
tracepath 8.8.8.8
# walks the path, tries different sizes

# View interface MTU
ip link show eth0
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...

# Change MTU
ip link set eth0 mtu 9000    # Jumbo frames (for 10GbE)
```

### Jumbo Frames

```
Standard Ethernet MTU = 1500 bytes.
Jumbo Frames - non-standard frames with MTU = 9000 bytes (most common).

Use cases:
  - Datacenter networks (10GbE, 25GbE, 100GbE)
  - iSCSI storage
  - HPC clusters

Advantages:
  - Fewer headers per unit of data
  - Fewer CPU interrupts (fewer packets to process)
  - Higher throughput for large transfers

Requirements:
  - Support on ALL devices in the path (switch, NIC, OS)
  - If any device does not support it → fragmentation or drops
```

### Fragmentation and Security

```
Security issues with fragmentation:

1. IDS/IPS evasion:
   An attack is split into fragments so that the IDS cannot
   reconstruct the payload, but the target host can.
   Different reassembly implementations → different behavior.

2. Overlapping fragments (Teardrop, Rose attacks):
   Overlapping fragments with different data in the overlapping area.
   OSes differ in which fragment "wins".
   Used to bypass ACLs and inject malicious payloads.

3. Fragment flooding (DoS):
   Flooding the victim with incomplete fragments
   → exhausting reassembly buffers → memory exhaustion.

4. Tiny fragment attack:
   Fragment 1: only IP header + 8 bytes of TCP (ports + seq)
   Fragment 2: remaining TCP flags (including those needed for filtering)
   Old ACLs inspected only the first fragment → bypass.
   Fix: block fragments with Offset=1 (8 bytes of data).

5. Consequence: many firewalls block IP fragments
   or require full reassembly before inspection (stateful firewall).
```

```
# View fragmentation statistics
cat /proc/net/snmp | grep Ip:
# Ip: ... ReasmReqds ReasmOKs ReasmFails FragOKs FragFails FragCreates

# More detail via nstat
nstat -az | grep -i frag
# IpReasmReqds    5    0.0  - fragments awaiting reassembly
# IpReasmOKs      2    0.0  - successful reassemblies
# IpReasmFails    0    0.0  - reassembly errors
# IpFragOKs       0    0.0  - successful fragmentations
# IpFragFails     0    0.0  - fragmentation errors
# IpFragCreates   0    0.0  - fragments created

# Capture fragmented packets
tcpdump -i eth0 '((ip[6:2] & 0x1fff) != 0) or ((ip[6] & 0x20) != 0)'
# Condition: Fragment Offset != 0 OR MF=1

# tcpdump simplified
tcpdump -i eth0 'ip[6] & 0x20 != 0'   # MF bit set (fragments)
```

## IPv4 vs IPv6: Fragmentation

```
IPv4:
  - Any router along the path can fragment packets
  - DF=0 by default (fragmentation allowed)
  - Identification in every packet (for reassembly)

IPv6:
  - Routers do NOT fragment packets at all
  - Only the sender performs fragmentation
  - If a packet does not fit → router sends ICMPv6 "Packet Too Big"
  - Sender reduces size (like PMTUD, but mandatory)
  - Fragmentation in IPv6 via Extension Header "Fragment Header" (44 bytes)
  - Minimum IPv6 MTU: 1280 bytes (RFC 8200)

Why did IPv6 remove router-level fragmentation?
  - Fragmentation is CPU-expensive (every packet must be split)
  - Reassembly at routers (if it existed) would be even more expensive
  - Security: fewer attack vectors through fragments
  - Predictability: one host is responsible for its own fragments
```

## Cheat Sheet

```
IP header (minimum 20 bytes):
  Ver=4, IHL=5 (20 bytes), TTL, Protocol, src/dst IP

TTL:
  Linux/macOS: 64    Windows: 128    Cisco: 255
  Each hop: TTL - 1
  TTL=0 → ICMP "Time Exceeded" (Type 11, Code 0) → to source
  traceroute: uses TTL from 1 to N to discover the path

Fragmentation flags:
  DF=1 → do not fragment
  MF=1 → more fragments follow
  MF=0 + Offset=0 → non-fragmented packet
  MF=0 + Offset>0 → last fragment

Fragment Offset:
  In 8-byte blocks (multiply by 8 for byte offset)
  All fragments of the same packet: same Identification

PMTUD:
  DF=1 + packet > MTU → ICMP "Fragmentation Needed" (Type 3, Code 4)
  Black Hole: ICMP blocked → use MSS Clamping

Useful commands:
  tcpdump -i eth0 -v icmp              - ICMP (TTL exceeded, frag needed)
  ping -M do -s 1472 8.8.8.8          - PMTU test
  traceroute -n 8.8.8.8               - path with TTL
  tracepath 8.8.8.8                   - PMTU Discovery along path
  ip route get 8.8.8.8                - MTU for route
  nstat -az | grep -i frag            - fragmentation stats
  tcpdump 'ip[6] & 0x20 != 0'         - catch fragments (MF=1)
```
