IP (Internet Protocol) - протокол сетевого уровня (L3 OSI), отвечающий за адресацию и маршрутизацию пакетов между хостами. Определён в RFC 791 (1981) для IPv4. IP - ненадёжный и без установки соединения: не гарантирует доставку, порядок или отсутствие дублей. Эти задачи решают протоколы транспортного уровня (TCP).

## Поля заголовка IPv4

### Version (4 бита)

```
Версия протокола IP.
4 = IPv4
6 = IPv6

Значение 4 (0100 в двоичной) присутствует в каждом IPv4 пакете.
Маршрутизатор смотрит именно это поле первым.
```

### IHL - Internet Header Length (4 бита)

```
Длина заголовка в 32-битных словах (4 байта).

Минимум: 5 (5 × 4 = 20 байт - заголовок без опций)
Максимум: 15 (15 × 4 = 60 байт - заголовок с опциями)

Почему нужно? Поле Options имеет переменную длину.
IHL указывает, где заканчивается заголовок и начинаются данные.

Формула: начало данных = IHL × 4 байт от начала пакета
```

### DSCP и ECN (ранее: Type of Service, 8 бит)

```
DSCP (Differentiated Services Code Point, 6 бит):
Приоритет пакета для QoS (Quality of Service).

Значения DSCP:
  000000 (CS0/BE)  - Best Effort, обычный трафик
  001000 (CS1)     - низкий приоритет
  010000 (CS2)     - обычный
  011000 (CS3)     - сигнализация (VoIP setup)
  100000 (CS4)     - видео
  101000 (CS5)     - голос (VoIP)
  110000 (CS6)     - сетевые протоколы (OSPF, BGP)
  111000 (CS7)     - зарезервирован

Предопределённые значения (Expedited/Assured Forwarding):
  EF  (101110) - Expedited Forwarding (VoIP, real-time)
  AF11-AF43    - Assured Forwarding (разные классы и приоритеты)

ECN (Explicit Congestion Notification, 2 бита):
  00 - Non ECN-Capable Transport
  01 или 10 - ECN Capable Transport (ECT)
  11 - Congestion Experienced (CE) - роутер обнаружил перегрузку
```

### Total Length (16 бит)

```
Полный размер IP пакета: заголовок + данные (в байтах).

Минимум: 20 байт (только заголовок, без данных)
Максимум: 65535 байт

На практике пакеты редко превышают MTU (1500 байт для Ethernet).
Пакеты больше MTU должны быть фрагментированы.

Полезное:
  Размер данных = Total Length - (IHL × 4)
```

### Identification (16 бит)

```
Уникальный идентификатор группы фрагментов.

Назначение:
- Все фрагменты одного пакета имеют одинаковый Identification.
- Получатель использует его для сборки (reassembly) фрагментов.

Генерация:
- Обычно монотонно увеличивающийся счётчик (per-source, per-dest).
- Некоторые ОС используют случайные значения (для безопасности).

Если пакет не фрагментирован (DF=1):
- Поле всё равно заполняется (правило RFC 791).
- Но фактически не используется при reassembly.
```

### Flags (3 бита)

```
Три бита управления фрагментацией:

Бит 0 (Reserved, Evil Bit): всегда 0
  Зарезервирован. RFC 3514 ("Evil Bit") - шутливый RFC,
  предлагавший устанавливать этот бит для вредоносных пакетов.

Бит 1 - DF (Don't Fragment):
  0 - можно фрагментировать
  1 - запрет фрагментации

  При DF=1 и пакет > MTU → маршрутизатор:
  - отбрасывает пакет
  - отправляет ICMP "Fragmentation Needed" (Type 3, Code 4) отправителю

  Используется в:
  - Path MTU Discovery (PMTUD)
  - TCP MSS negotiation
  - GRE, IPsec туннели

Бит 2 - MF (More Fragments):
  0 - это последний (или единственный) фрагмент
  1 - за этим фрагментом следуют ещё

  Последний фрагмент: MF=0, Fragment Offset > 0
  Нефрагментированный пакет: MF=0, Fragment Offset=0

Примеры:
  Flags = 0x00 (000) - не фрагментирован, последний
  Flags = 0x40 (010) - DF=1, не фрагментировать
  Flags = 0x20 (001) - MF=1, промежуточный фрагмент
```

### Fragment Offset (13 бит)

```
Позиция данного фрагмента в оригинальном пакете.
Измеряется в 8-байтных блоках (не в байтах!).

Реальный байтовый offset = Fragment Offset × 8

Максимальный offset: 8191 × 8 = 65528 байт

Почему × 8?
  13 бит дают max 8191, умножаем на 8 → 65528 байт.
  Это почти покрывает максимум IP пакета (65535 байт).
  Шаг 8 байт - каждый фрагмент (кроме последнего) должен
  иметь длину данных, кратную 8 байтам.

Пример для пакета 4000 байт, MTU=1500:
  Фрагмент 1: offset=0    (байты 0-1479)
  Фрагмент 2: offset=185  (185 × 8 = 1480, байты 1480-2959)
  Фрагмент 3: offset=370  (370 × 8 = 2960, байты 2960-3999)
```

### TTL - Time To Live (8 бит)

Подробно разобран в отдельном разделе ниже.

### Protocol (8 бит)

```
Протокол верхнего уровня (что находится в поле данных).

Значения IANA:
  1   - ICMP  (ping, traceroute)
  2   - IGMP  (multicast)
  6   - TCP   (надёжная доставка)
  17  - UDP   (без установки соединения)
  41  - IPv6 (encapsulated)
  47  - GRE   (туннели)
  50  - ESP   (IPsec, шифрование)
  51  - AH    (IPsec, аутентификация)
  89  - OSPF  (маршрутизация)
  132 - SCTP

Посмотреть полный список:
  cat /etc/protocols
```

### Header Checksum (16 бит)

```
Контрольная сумма ТОЛЬКО заголовка IP (не данных!).
Данные защищают протоколы L4 (TCP/UDP checksum).

Особенность: пересчитывается каждым маршрутизатором.
Почему? TTL уменьшается на каждом хопе → заголовок меняется
→ старая сумма становится неверной.

Алгоритм: дополнение до единицы суммы 16-битных слов заголовка.

Если checksum не совпадает → пакет отбрасывается молча (без уведомления).
```

### Source и Destination IP (по 32 бита)

```
Source IP      - адрес отправителя
Destination IP - адрес получателя

Оба в формате IPv4 (4 октета по 8 бит).
Пример: 192.168.1.10 = 0xC0A8010A

Важно: Source IP может быть поддельным (IP spoofing).
Маршрутизаторы не проверяют, реально ли принадлежит адрес отправителю.
Защита - BCP38 (ingress filtering) на границах сетей.
```

### Options (0-40 байт)

```
Опциональные поля. Редко используются в современных сетях
(мешают hardware offloading, часто блокируются).

Примеры опций:
  Record Route (7)    - каждый маршрутизатор записывает свой IP
  Timestamp (68)      - каждый хоп добавляет timestamp
  Strict Source Route - жёстко заданный путь (все хопы)
  Loose Source Route  - часть хопов задана
  Router Alert (148)  - попросить маршрутизаторы обработать пакет

Проблемы:
  Любой пакет с Options обрабатывается CPU маршрутизатора
  (не hardware fast path) → медленнее и потенциально уязвимо.

Увеличивают IHL: если Options присутствуют, IHL > 5.
```

## TTL - Time To Live

### Что такое TTL

```
TTL (Time To Live) - счётчик жизни пакета в сети.
Диапазон: 0-255 (8 бит).

Каждый маршрутизатор, через который проходит пакет:
  1. Уменьшает TTL на 1
  2. Если TTL стало 0 → отбрасывает пакет
  3. Отправляет ICMP "Time Exceeded" (Type 11, Code 0) источнику

Цель: предотвратить бесконечную циркуляцию пакетов
при петлях маршрутизации (routing loops).

Важно: TTL измеряется в хопах (прыжках), НЕ в секундах.
Хотя RFC 791 задумывал это как секунды, на практике
каждый хоп = -1 к TTL (даже если маршрутизатор обрабатывает пакет мгновенно).
```

### Начальные значения TTL по умолчанию

```
ОС / Устройство            Начальное TTL
─────────────────────────────────────────
Linux (современные)             64
Windows (XP+)                  128
macOS / iOS                     64
Cisco IOS (router)             255
Solaris / AIX                  255
FreeBSD / OpenBSD               64
Android                         64
Windows 95/NT                  128
Windows 2000/XP (ранние)        32

Эти значения настраиваются:
  Linux:   /proc/sys/net/ipv4/ip_default_ttl
  Windows: HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\DefaultTTL
```

### Как работает TTL на каждом хопе

```
Отправитель               R1              R2             Получатель
TTL=64 ──────────────────► TTL=63 ─────►TTL=62 ──────►  принят

Если пакет не доходит:
TTL=3 ────► TTL=2 ────► TTL=1 ────► TTL=0
                                     ↓
                         R3 отбрасывает пакет
                         R3 отправляет ICMP "Time Exceeded" → источнику
                         (ICMP Type 11, Code 0)
```

### Определение ОС по TTL (OS Fingerprinting)

```
Зная TTL в ответном пакете и примерное расстояние (хопы),
можно угадать ОС отправителя:

ping 8.8.8.8 → TTL=117 в ответе
  Типичные начальные значения: 64, 128, 255
  117 близко к 128 - 11 хопов → вероятно Windows

ping linux-host → TTL=62 в ответе
  62 близко к 64 - 2 хопа → вероятно Linux/macOS

Это основа пассивного fingerprinting (p0f, nmap -O).
Точность снижается если TTL настроен нестандартно.

Практика:
  TTL в ответе 64±10  → Linux/macOS/FreeBSD (начальный 64)
  TTL в ответе 128±15 → Windows (начальный 128)
  TTL в ответе 255±15 → Cisco IOS / Solaris (начальный 255)
```

### TTL и traceroute

```
traceroute использует TTL для определения пути пакета:

1. Отправить пакет с TTL=1 → первый маршрутизатор отбрасывает,
   возвращает ICMP "Time Exceeded" → мы узнаём IP первого хопа.

2. TTL=2 → второй хоп возвращает ICMP → IP второго хопа.

3. Повторяем до получения ICMP "Destination Unreachable" или
   ICMP Echo Reply от цели.

Реализации traceroute:
  Linux (traceroute): UDP пакеты на порты 33434+ (по умолчанию)
  Linux (tracepath):  UDP, без root
  Windows (tracert):  ICMP Echo Request
  Вариант TCP:        tcptraceroute, hping3 -S

Проблема: файерволлы часто блокируют UDP/ICMP → звёздочки (*).
Решение: tcptraceroute (TCP SYN на порт 80/443 - обычно пропускают).
```

```
# traceroute к цели
traceroute 8.8.8.8
traceroute -I 8.8.8.8       # ICMP вместо UDP
traceroute -T -p 80 8.8.8.8 # TCP SYN на порт 80
traceroute -n 8.8.8.8       # без резолва DNS

# Windows
tracert 8.8.8.8

# Показать TTL в ping ответе
ping -c 3 8.8.8.8

# Посмотреть TTL пакета в tcpdump
tcpdump -i eth0 -v 'icmp'
# 192.168.1.10 > 8.8.8.8: ICMP echo request, id 1, seq 1, length 64
# (tos 0x0, ttl 64, id 12345, offset 0, flags [DF], ...)

# Изменить TTL отправки (Linux)
ping -t 5 8.8.8.8            # macOS: -m 5
hping3 --ttl 5 8.8.8.8       # задать точный TTL

# Изменить default TTL системы
echo 128 > /proc/sys/net/ipv4/ip_default_ttl

# Постоянно (через sysctl)
echo "net.ipv4.ip_default_ttl = 128" >> /etc/sysctl.conf
sysctl -p
```

### TTL и безопасность

```
TTL-based атаки:

1. TTL-based evasion:
   IDS/IPS видит пакет с TTL=1, но целевой хост не получит его.
   Атакующий может строить пакеты, которые IDS видит,
   а хост - нет (или наоборот). Основа некоторых техник обхода IDS.

2. IP Spoofing + малый TTL:
   Пакеты с поддельным src IP и TTL=1 → не долетят до жертвы spoofing,
   но могут вызвать ICMP "Time Exceeded" к поддельному адресу.

3. Определение топологии сети (разведка):
   Анализ TTL в ответах для построения карты сети.

4. Кольца маршрутизации (routing loops):
   TTL - единственная защита от пакетов, вечно гуляющих по петле.
   При отсутствии TTL: пакет мог бы циркулировать бесконечно.
```

## Фрагментация IP

### Зачем нужна фрагментация

```
Разные сетевые технологии имеют разный MTU (Maximum Transmission Unit):

Технология            MTU (байт)
──────────────────────────────────
Ethernet               1500
Wi-Fi (802.11)         2304
PPPoE (DSL)            1492
Loopback              65536
GRE туннель           1476 (1500 - 24 GRE header)
IPsec (ESP)           ~1422 (зависит от cipher/auth)
VXLAN                 1450

Если IP пакет > MTU следующего хопа:
  - без DF: маршрутизатор фрагментирует пакет на части <= MTU
  - с DF=1: маршрутизатор отбрасывает и шлёт ICMP "Fragmentation Needed"
```

### Как происходит фрагментация

```
Оригинальный пакет: 4000 байт данных, MTU=1500

IP заголовок: 20 байт
Данные: 4000 байт
Итого: 4020 байт > 1500 (MTU)

Каждый фрагмент:
  Максимум данных на фрагмент = MTU - IP заголовок = 1500 - 20 = 1480 байт
  1480 должно делиться на 8 (для Fragment Offset)
  1480 / 8 = 185 → ровно делится, хорошо

Фрагментация 4000 байт данных:
┌─────────────────────────────────────────────────────────┐
│  Фрагмент 1                                              │
│  IP header: ID=12345, MF=1, Offset=0, Total=1500        │
│  Данные: байты 0-1479 (1480 байт)                        │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│  Фрагмент 2                                              │
│  IP header: ID=12345, MF=1, Offset=185, Total=1500      │
│  Данные: байты 1480-2959 (1480 байт)                     │
│  (Offset 185 × 8 = 1480)                                 │
└─────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────┐
│  Фрагмент 3                                              │
│  IP header: ID=12345, MF=0, Offset=370, Total=1060      │
│  Данные: байты 2960-3999 (1040 байт)                     │
│  (Offset 370 × 8 = 2960)                                 │
│  (MF=0 - последний фрагмент!)                            │
└─────────────────────────────────────────────────────────┘
```

### Правила фрагментации (RFC 791)

```
1. Все фрагменты одного пакета имеют одинаковое Identification.

2. Все фрагменты (кроме последнего) имеют длину данных, кратную 8 байтам.
   (требование Fragment Offset, который считается в 8-байтных блоках)

3. MF=1 для всех фрагментов, кроме последнего.

4. Последний фрагмент: MF=0, Offset > 0 (если фрагментация была).

5. Каждый фрагмент - полноценный IP пакет со своим заголовком.
   Маршрутизаторы могут снова фрагментировать фрагменты.

6. Сборка (reassembly) происходит только на конечном хосте-получателе,
   НЕ на промежуточных маршрутизаторах.
   (В отличие от IPv6, где фрагментация вообще нет на маршрутизаторах)

7. Таймаут сборки: если не все фрагменты пришли за ~15-30 сек →
   все полученные фрагменты отбрасываются,
   ICMP "Time Exceeded, Fragment Reassembly" (Type 11, Code 1) → источнику.
```

### Reassembly (сборка) на получателе

```
Получатель собирает оригинальный пакет:

1. При приходе первого фрагмента (MF=1 или Offset>0):
   - Создаётся буфер reassembly, ключ: (src IP, dst IP, Protocol, ID)
   - Запускается таймер (обычно 15-30 секунд)

2. Каждый новый фрагмент добавляется в буфер по своему Offset.

3. Сборка завершена когда:
   - Получен фрагмент с MF=0 (знаем полный размер)
   - Все байты от 0 до конца без пропусков присутствуют

4. Если таймер истёк до полной сборки → ICMP Type 11, Code 1 → источнику.

Атака Teardrop:
   Перекрывающиеся фрагменты (overlapping offsets)
   вызывали переполнение буфера в старых ОС (Windows 95/98/NT).
   Современные ОС обрабатывают корректно.
```

### Path MTU Discovery (PMTUD)

```
Механизм автоматического определения минимального MTU на всём пути.
Позволяет избежать фрагментации в сети.

Принцип работы:
1. Отправитель устанавливает DF=1 (Don't Fragment).
2. Отправляет пакет размером текущего PMTU (начально - MTU интерфейса).
3. Если пакет > MTU где-то на пути:
   - Маршрутизатор отбрасывает пакет
   - Отправляет ICMP Type 3, Code 4 "Fragmentation Needed"
   - В ICMP-сообщении - MTU следующего хопа (RFC 1191)
4. Отправитель уменьшает PMTU до значения из ICMP.
5. Повторяет до тех пор, пока пакеты проходят.

Проблема: Black Hole PMTUD
   Многие файерволлы блокируют ICMP Type 3 → отправитель
   не получает "Fragmentation Needed" → соединение висит.

Симптом: соединение устанавливается (handshake проходит, маленькие пакеты),
         но большие данные (HTTP, файлы) не передаются.

Решения для Black Hole:
   TCP MSS Clamping (на маршрутизаторах/файерволлах):
     iptables -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
       -j TCPMSS --clamp-mss-to-pmtu

   PLPMTUD (Packetization Layer PMTU Discovery, RFC 4821):
     Определение PMTU на уровне L4, без ICMP.
```

```
# Посмотреть PMTU для маршрута
ip route get 8.8.8.8
# 8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10 uid 1000
#   cache  mtu 1500

# Кэш PMTU
ip route show cache

# Тест PMTU вручную
ping -c 3 -M do -s 1472 8.8.8.8
# -M do = DF bit set
# -s 1472 = данные 1472 байт + 8 ICMP + 20 IP = 1500 (ровно MTU)

# Если ответ: "Frag needed and DF set (mtu = 1492)"
# - где-то на пути MTU меньше 1500

# Найти PMTU через tracepath (без root)
tracepath 8.8.8.8
# проходит по пути, пробует разные размеры

# Посмотреть MTU интерфейса
ip link show eth0
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...

# Изменить MTU
ip link set eth0 mtu 9000    # Jumbo frames (для 10GbE)
```

### Jumbo Frames

```
Стандартный Ethernet MTU = 1500 байт.
Jumbo Frames - нестандартные кадры с MTU = 9000 байт (чаще всего).

Применение:
  - Datacenter сети (10GbE, 25GbE, 100GbE)
  - iSCSI хранилища
  - HPC кластеры

Преимущества:
  - Меньше заголовков на одинаковый объём данных
  - Меньше прерываний CPU (меньше пакетов)
  - Выше пропускная способность для больших передач

Требования:
  - Поддержка на ВСЕХ устройствах пути (switch, NIC, ОС)
  - Если хоть одно устройство не поддерживает → фрагментация или потеря
```

### Фрагментация и безопасность

```
Проблемы безопасности с фрагментацией:

1. IDS/IPS evasion (обход систем обнаружения):
   Атака разбивается на фрагменты так, чтобы IDS не мог
   восстановить содержимое, а хост-жертва - мог.
   Разные реализации reassembly → разное поведение.

2. Overlapping fragments (Teardrop, Rose атаки):
   Перекрывающиеся фрагменты с разными данными в области перекрытия.
   ОС по-разному выбирают, какой фрагмент "победит".
   Использовалось для обхода ACL и вставки вредоносного кода.

3. Fragment flooding (DoS):
   Заваливание жертвы незавершёнными фрагментами
   → истощение буферов reassembly → нехватка памяти.

4. Tiny fragment attack:
   Фрагмент 1: только IP заголовок + 8 байт TCP (порты + seq)
   Фрагмент 2: остальные TCP флаги (в т.ч. нужные для фильтрации)
   Старые ACL проверяли только первый фрагмент → bypass.
   Решение: блокировать фрагменты с Offset=1 (8 байт данных).

5. Последствие: многие файерволлы блокируют IP фрагменты
   или требуют полной сборки перед инспекцией (stateful firewall).
```

```
# Посмотреть статистику фрагментации
cat /proc/net/snmp | grep Ip:
# Ip: ... ReasmReqds ReasmOKs ReasmFails FragOKs FragFails FragCreates

# Детальнее через nstat
nstat -az | grep -i frag
# IpInUnknownProtos      0        0.0
# IpReasmReqds           5        0.0  - фрагментов на сборку
# IpReasmOKs             2        0.0  - успешных сборок
# IpReasmFails           0        0.0  - ошибок сборки
# IpFragOKs              0        0.0  - успешных фрагментаций
# IpFragFails            0        0.0  - ошибок фрагментации
# IpFragCreates          0        0.0  - создано фрагментов

# Захват фрагментированных пакетов
tcpdump -i eth0 '((ip[6:2] & 0x1fff) != 0) or ((ip[6] & 0x20) != 0)'
# Условие: Fragment Offset != 0 OR MF=1

# tcpdump упрощённо
tcpdump -i eth0 'ip[6] & 0x20 != 0'   # MF bit set (фрагменты)
```

## IPv4 vs IPv6: фрагментация

```
IPv4:
  - Фрагментацию может делать любой маршрутизатор на пути
  - DF=0 по умолчанию (разрешена фрагментация)
  - Identification в каждом пакете (для reassembly)

IPv6:
  - Маршрутизаторы НЕ фрагментируют пакеты вообще
  - Фрагментацию делает только отправитель
  - Если пакет не помещается → маршрутизатор шлёт ICMPv6 "Packet Too Big"
  - Отправитель уменьшает размер (аналог PMTUD, но обязательный)
  - Фрагментация в IPv6 через Extension Header "Fragment Header" (44 байт)
  - Минимальный MTU IPv6: 1280 байт (RFC 8200)

Почему IPv6 убрал фрагментацию на маршрутизаторах?
  - Фрагментация дорогая по CPU (каждый пакет надо разбирать)
  - Reassembly на маршрутизаторах (если бы было) - ещё дороже
  - Безопасность: меньше векторов атак через фрагменты
  - Предсказуемость: один хост отвечает за свои фрагменты
```

## Шпаргалка

```
IP заголовок (минимум 20 байт):
  Ver=4, IHL=5 (20 байт), TTL, Protocol, src/dst IP

TTL:
  Linux/macOS: 64    Windows: 128    Cisco: 255
  Каждый хоп: TTL - 1
  TTL=0 → ICMP "Time Exceeded" (Type 11, Code 0) → источнику
  traceroute: использует TTL от 1 до N для определения пути

Флаги фрагментации:
  DF=1 → нельзя фрагментировать
  MF=1 → есть ещё фрагменты за этим
  MF=0 + Offset=0 → нефрагментированный пакет
  MF=0 + Offset>0 → последний фрагмент

Fragment Offset:
  В 8-байтных блоках (умножить на 8 для байтового смещения)
  Все фрагменты одного пакета: одинаковый Identification

PMTUD:
  DF=1 + пакет > MTU → ICMP "Fragmentation Needed" (Type 3, Code 4)
  Black Hole: ICMP блокируется → используй MSS Clamping

Полезные команды:
  tcpdump -i eth0 -v icmp              - ICMP (TTL exceeded, frag needed)
  ping -M do -s 1472 8.8.8.8          - тест PMTU
  traceroute -n 8.8.8.8               - путь с TTL
  tracepath 8.8.8.8                   - PMTU Discovery на пути
  ip route get 8.8.8.8                - MTU для маршрута
  nstat -az | grep -i frag            - статистика фрагментации
  tcpdump 'ip[6] & 0x20 != 0'         - поймать фрагменты (MF=1)
```
