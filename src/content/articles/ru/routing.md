## Введение

Маршрутизация - это процесс выбора пути для передачи пакетов между сетями. Когда PC1 отправляет пакет в сеть 192.168.2.0/24, он не знает как туда добраться - он просто передаёт пакет своему шлюзу. Дальше работают роутеры: каждый смотрит в свою таблицу маршрутов и решает куда передать пакет дальше.

В данной работе мы построим топологию с тремя роутерами в GNS3, настроим IP-адреса на всех интерфейсах, разберём статическую маршрутизацию с нуля, захватим трафик через Wireshark и изучим поведение TTL, а затем перейдём на OSPF и убедимся что сеть перестраивается автоматически при падении линка.

| Параметр | Значение |
| --- | --- |
| Среда | GNS3 |
| Устройства | 3× Router (R1, R2, R3), 3× VPC (PC1, PC2, PC3) |
| Захват трафика | Wireshark |
| Протоколы | Static routing → OSPF |

## Теоретическая база

### Как работает таблица маршрутов

Каждый роутер принимает решение локально - он не знает всю топологию, только свою таблицу. Пакет идёт hop-by-hop:

```
PC1 → Router1 → Router2 → PC2
       смотрит    смотрит
       свою       свою
       таблицу    таблицу
```

### Статика vs OSPF

| Параметр | Статические маршруты | OSPF |
| --- | --- | --- |
| Настройка | Вручную на каждом роутере | Один раз - роутеры договорятся сами |
| Реакция на сбой | Никакой - пакеты уйдут в никуда | Автоматический пересчёт за секунды |
| Масштаб | Подходит до ~5 роутеров | Сети любого размера |
| Нагрузка на CPU | Минимальная | Средняя (рассылка LSA, вычисление SPF) |

### Что такое TTL

TTL (Time to Live) - счётчик в IP-заголовке. Каждый роутер уменьшает TTL на 1. Когда TTL = 0, роутер дропает пакет и отправляет ICMP Time Exceeded отправителю. Именно на этом механизме работает traceroute.

### Шаг 1. Исходная топология

Строим базовую схему: два роутера и два хоста.


IP-адрес `192.168.1.2`, маска `/24`, шлюз `192.168.1.1` - это интерфейс R1 Fa0/0.

![02_pc1](/handson/images/routing_net/02_pc1.png)

### Шаг 3. Настройка PC2

```
ip 192.168.2.2/24 192.168.2.1
```

Шлюз `192.168.2.1` - интерфейс R2 Fa0/1.

![03_pc2](/handson/images/routing_net/03_pc2.png)

### Шаг 4. R1 - интерфейс Fa0/0 (сторона PC1)

```

```

![04_inter_f0](/handson/images/routing_net/04_inter_f0.png)

## Фаза 2. Статическая маршрутизация

### Шаг 10. Проверяем связность до настройки маршрутов

```
PC1> ping 192.168.2.2
```

Ping не проходит - `Destination host unreachable`. R1 знает только о своих подсетях и не знает как добраться до 192.168.2.0/24.

![10_test](/handson/images/routing_net/10_test.png)

### Шаг 11. Добавляем маршрут на R1

```
ip route 192.168.2.0 255.255.255.0 10.0.12.2
```

Говорим R1: пакеты в сеть `192.168.2.0/24` отправлять через соседа `10.0.12.2` (R2).

![11_ip_route](/handson/images/routing_net/11_ip_route.png)

### Шаг 12. Таблица маршрутов R1

```
show ip route
```

```
C    192.168.1.0/24  is directly connected, Fa0/0
C    10.0.12.0/30    is directly connected, Fa0/1
S    192.168.2.0/24  [1/0] via 10.0.12.2
```

`S` = Static, `[1/0]` = Administrative Distance / Metric.

![12_show_ip_route](/handson/images/routing_net/12_show_ip_route.png)

### Шаг 13. Добавляем маршрут на R2

R2 тоже должен знать как ответить обратно в сеть 192.168.1.0/24:

```
ip route 192.168.1.0 255.255.255.0 10.0.12.1
```

![13_ip_route](/handson/images/routing_net/13_ip_route.png)

### Шаг 14. Таблица маршрутов R2

```
show ip route
```

```
C    10.0.12.0/30    is directly connected, Fa0/0
S    192.168.1.0/24  [1/0] via 10.0.12.1
C    192.168.2.0/24  is directly connected, Fa0/1
```

![14_show_ip_route](/handson/images/routing_net/14_show_ip_route.png)

### Шаг 15. Проверяем ping - теперь работает

```
PC1> ping 192.168.2.2
```

Все 5 пакетов получены. Статическая маршрутизация настроена.

![15_test_success](/handson/images/routing_net/15_test_success.png)

## Фаза 3. Анализ трафика - Wireshark и TTL

### Шаг 16. Traceroute от PC1 до PC2

```
PC1> trace 192.168.2.2
```

```
1   192.168.1.1   18 ms    ← R1
2   10.0.12.2     59 ms    ← R2
3   192.168.2.2   ---      ← PC2 (port unreachable - UDP порт traceroute закрыт)
```

Видны все хопы на пути до PC2.

![16_trace](/handson/images/routing_net/16_trace.png)

### Шаг 17. Запускаем захват трафика между R1 и R2

В Packet Tracer кликаем на линк между R1 и R2 → открывается интерфейс захвата пакетов.

![17_r1_r2](/handson/images/routing_net/17_r1_r2.png)

### Шаг 18. ICMP пакеты в Wireshark

Запускаем `ping 192.168.2.2` с PC1 и смотрим дамп:

- ICMP Echo Request от `192.168.1.2` к `192.168.2.2`
- Между ними видны CDP-пакеты (Cisco Discovery Protocol)

![18_icmp](/handson/images/routing_net/18_icmp.png)

### Шаг 19. Разбираем IP-заголовок - смотрим TTL

Кликаем на ICMP Echo Request → разворачиваем `Internet Protocol`:

```
Source:          192.168.1.2
Destination:     192.168.2.2
Time to Live:    63
Protocol:        ICMP (1)
```

> TTL = 63, а не 64. PC1 отправил пакет с TTL=64, R1 уменьшил на 1 при пересылке. Именно так роутеры считают хопы и предотвращают бесконечную петлю пакетов в сети.

![19_icmp_req_ttl](/handson/images/routing_net/19_icmp_req_ttl.png)

### Шаг 20. Time-to-live exceeded при traceroute

При трассировке видны пакеты с TTL=1 - R1 их дропает и отвечает ICMP Time Exceeded. Это и есть механизм traceroute: каждый следующий пакет имеет TTL на 1 больше, пока не дойдёт до цели.

![20_trace](/handson/images/routing_net/20_trace.png)

Отключаем линк между R1 и R2 - симулируем обрыв канала.

![29_suspend](/handson/images/routing_net/29_suspend.png)

### Шаг 30. Ping теряет пакеты

```
PC1> ping 192.168.2.2
```

Пинги нестабильны - видны потери пакетов. Статические маршруты не реагируют на падение линка автоматически.

![30_ping](/handson/images/routing_net/30_ping.png)

### Шаг 31. Таблица маршрутов R1 после shutdown

```
R1(config)# interface Fa0/1
R1(config-if)# shutdown

R1# show ip route
```

В таблице остался только один connected маршрут - `C 192.168.1.0/24`. Все статические маршруты исчезли: next-hop `10.0.12.2` недоступен, поэтому Cisco убрала их из таблицы.

> Это главная проблема статической маршрутизации: при отключении линка маршруты «пропадают», и пакеты некуда отправить. Администратор должен вручную добавлять резервные маршруты или менять топологию. Именно для решения этой проблемы существует OSPF.

![31_no_routes](/handson/images/routing_net/31_no_routes.png)

```

```

После включения интерфейса связь восстанавливается, но первые пакеты теряются - роутер ждёт пока интерфейс перейдёт в состояние up/up.

## Фаза 6. OSPF - переходим на динамическую маршрутизацию

### Шаг 33. Удаляем статику на R1

```
no ip route 192.168.2.0 255.255.255.0 10.0.12.2
no ip route 192.168.3.0 255.255.255.0 10.0.12.2
```

![33_no_route_r1](/handson/images/routing_net/33_no_route_r1.png)

### Шаг 34. Удаляем статику на R2

```
no ip route 192.168.1.0 255.255.255.0 10.0.12.1
no ip route 192.168.3.0 255.255.255.0 10.0.23.2
```

![34_no_route_r2](/handson/images/routing_net/34_no_route_r2.png)

### Шаг 35. Удаляем статику на R3

```
no ip route 192.168.1.0 255.255.255.0 10.0.23.1
no ip route 192.168.2.0 255.255.255.0 10.0.23.1
```

![35_no_route_r3](/handson/images/routing_net/35_no_route_r3.png)

### Шаг 36. Включаем OSPF на R1

```
router ospf 1
network 192.168.1.0 0.0.0.255 area 0
network 10.0.12.0 0.0.0.3 area 0
```

`process ID = 1` - локально значим, не обязан совпадать на разных роутерах. Маска `0.0.0.255` - wildcard (инверсия маски подсети). `area 0` - магистральная область OSPF, обязательна.

![36_ospf_r1](/handson/images/routing_net/36_ospf_r1.png)

### Шаг 37. OSPF на R2

```
router ospf 1
network 10.0.12.0 0.0.0.3 area 0
network 10.0.23.0 0.0.0.3 area 0
network 192.168.2.0 0.0.0.255 area 0
```

![37_ospf_r2](/handson/images/routing_net/37_ospf_r2.png)

### Шаг 38. OSPF на R3

```
router ospf 1
network 10.0.23.0 0.0.0.3 area 0
network 192.168.3.0 0.0.0.255 area 0
```

После ввода команд в консоли появляется сообщение `%OSPF-5-ADJCHG` - это означает что R3 установил соседство с R2 и они перешли в состояние `FULL`.

![38_ospf_r3](/handson/images/routing_net/38_ospf_r3.png)

### Шаг 39. Проверяем OSPF на R1

```
show ip ospf neighbor
show ip route
```

```
Neighbor ID    State    Interface
192.168.2.1    FULL/DR  Fa0/1     ← сосед R2, состояние FULL
```

```
O    10.0.23.0/30   [110/2] via 10.0.12.2   ← узнано по OSPF
O    192.168.3.0/24 [110/3] via 10.0.12.2   ← сеть PC3, метрика 3
```

`O` = OSPF. `[110/2]` = Administrative Distance 110 / Cost 2. R1 автоматически узнал о сетях за R3 - без единой статической записи.

![39_ospf_check](/handson/images/routing_net/39_ospf_check.png)

### Шаг 40. Итоговая проверка

```
PC1> ping 192.168.2.2
PC1> ping 192.168.3.2
```

Оба пинга проходят. OSPF самостоятельно построил таблицы маршрутизации на всех трёх роутерах.

![40_ospf_works](/handson/images/routing_net/40_ospf_works.png)

## Итоги и выводы

### Итоговая схема сети

```
PC1 (192.168.1.2)
        |
       R1 (Fa0/0: 192.168.1.1 | Fa0/1: 10.0.12.1)
        |
   10.0.12.0/30
        |
       R2 (Fa0/0: 10.0.12.2 | Fa0/1: 192.168.2.1 | Fa1/0: 10.0.23.1)
        |                         |
PC2 (192.168.2.2)           10.0.23.0/30
                                  |
                                 R3 (Fa0/0: 10.0.23.2 | Fa0/1: 192.168.3.1)
                                  |
                            PC3 (192.168.3.2)
```

### Сравнение подходов

| Характеристика | Статическая маршрутизация | OSPF |
| --- | --- | --- |
| Настройка | Вручную на каждом роутере | Один раз - `network` команды |
| Реакция на сбой | Маршруты пропадают, пакеты теряются | Автоматический пересчёт за секунды |
| При добавлении роутера | Нужно обновить маршруты везде | Роутер сам объявит свои сети |
| Нагрузка на CPU | Минимальная | Средняя (LSA, алгоритм Дейкстры) |
| Масштабируемость | Плохая | Отличная |

### Ключевые выводы

Статическая маршрутизация хорошо подходит для маленьких сетей с неизменной топологией - всё предсказуемо и прозрачно. При расширении сети количество маршрутов растёт очень быстро: при добавлении каждого нового роутера нужно обновлять записи на всех остальных.

Главная проблема статики - отсутствие реакции на сбой. При падении линка маршруты исчезают из таблицы, и трафик идёт в никуда до тех пор пока администратор не вмешается вручную.

OSPF решает эту проблему: роутеры сами обнаруживают соседей через Hello-пакеты, обмениваются информацией о топологии через LSA (Link State Advertisement) и строят таблицу маршрутизации с помощью алгоритма Дейкстры. При падении линка OSPF пересчитывает маршруты автоматически.

Метрика OSPF - это суммарный cost по пути, где cost каждого интерфейса = 10⁸ / bandwidth. Состояние `FULL/DR` означает что в сегменте выбран Designated Router - на линке 10.0.12.0/30 им стал R2.
